# Research: Architecting an ANSI Colorscheme Auditor & Checker in Lua
**Design Specification, Colorimetry Science, and Architectural Blueprint for Extreme Correctness and Simplicity**

---

## 1. Executive Summary & Problem Space

Terminal colorschemes (the classic 16 ANSI colors, plus default foreground, background, cursor, and selection) are foundational to daily developer ergonomics. Despite their ubiquity, creating an ANSI colorscheme is notoriously error-prone:
- **Illegible Muted Elements**: ANSI 8 (Bright Black / Dark Gray), often used for code comments and line numbers, routinely falls below readable contrast thresholds against dark terminal backgrounds.
- **Dark-on-Dark Contrast Failures**: Standard dark ANSI Blue (ANSI 4) frequently collapses into near-invisibility on modern dark backgrounds ($L^* < 15$).
- **Colorblind Inaccessibility**: In source control diffs, ANSI 1 (Red/deletion) and ANSI 2 (Green/addition) often have nearly identical perceptual lightness ($L$). For 8% of male developers with deuteranomaly or protanomaly, additions and deletions become indistinguishable.
- **Inverted Lightness Hierarchies**: The ANSI specification pairs normal colors (0–7) with "bright" / "bold" counterparts (8–15). Many themes inadvertently make bright variants *darker* or lower-chroma than normal variants.
- **Semantic Token Collisions**: Syntax highlighting engines map abstract syntax tree tokens (types, constants, functions, strings) to ANSI colors. Themes frequently contain color pairs with near-zero perceptual distance ($\Delta E$), causing distinct syntax elements to look identical.

Existing terminal color tools are predominantly simple visual test-pattern scripts (e.g., `colortest`, `theme.sh`) or basic WCAG 2.1 linters that only measure simple relative luminance ratios. 

To achieve **extreme correctness** without sacrificing **simplicity**, a modern colorscheme auditor must:
1. **Adhere to modern color science**: Use linearized sRGB, the **Oklab / Oklch** color space (Björn Ottosson, 2020) for perceptual distance and lightness, and **APCA** (Accessible Perceptual Contrast Algorithm / WCAG 3 candidate) alongside **WCAG 2.1**.
2. **Simulate Color Vision Deficiency (CVD)**: Use physiologically validated projection matrices (Machado et al. 2009 / Viénot et al. 1999) to verify diff and syntax discriminability for protanopia, deuteranopia, and tritanopia.
3. **Audit ANSI-specific terminal semantics**: Validate lightness monotonicity across normal/bright pairs, hue sector fidelity, reverse-video legibility, and comment contrast.
4. **Remain ultra-simple in Lua**: Pure Lua (5.1+, LuaJIT, and Neovim compatible), zero external dependencies, mathematically exact, and deterministic.

## 2. Colorimetry & Mathematical Foundations

### 2.1. The Fallacy of Naive RGB & WCAG 2.1
Most naive color tools calculate brightness or contrast using simple formulas like:
$$Y_{\text{naive}} = 0.299 R + 0.587 G + 0.114 B$$
This equation operates on non-linear (gamma-compressed) display values and is physically invalid for contrast calculations.

Even the standard **WCAG 2.1 contrast ratio**:
$$\text{CR} = \frac{Y_1 + 0.05}{Y_2 + 0.05}$$
is known to fail for dark-mode interfaces:
- It dramatically overstates the perceived contrast of pure blues and dark saturated colors on dark backgrounds.
- It does not account for display spatial frequency or human local adaptation (pupillary and neural adaptation).
- It treats contrast symmetrically, ignoring the fact that light text on dark backgrounds causes "halation" (optical blooming) in the human eye.

### 2.2. Exact sRGB Linearization (Gamma Expansion)
All RGB values from hex codes (`#RRGGBB`) must first be normalized to $[0, 1]$ and then linearized using the piecewise sRGB transfer function (IEC 61966-2-1:1999):

$$C_{\text{linear}} = \begin{cases} 
\frac{C_{\text{sRGB}}}{12.92} & \text{if } C_{\text{sRGB}} \le 0.04045 \\
\left(\frac{C_{\text{sRGB}} + 0.055}{1.055}\right)^{2.4} & \text{if } C_{\text{sRGB}} > 0.04045
\end{cases}$$

```lua
local function srgb_to_linear(c)
  if c <= 0.04045 then
    return c / 12.92
  else
    return ((c + 0.055) / 1.055) ^ 2.4
  end
end
```

### 2.3. APCA (Accessible Perceptual Contrast Algorithm)
APCA (developed by Andrew Somers for WCAG 3) models human contrast perception with higher fidelity, accounting for polarity (light text on dark background vs. dark text on light background), non-linear cone response, and black flare:

1. **Screen Luminance ($Y_s$) with Black Clamping**:
   Linearize channels via $C^{2.4}$, calculate raw luminance $Y = 0.2126729 R + 0.7151522 G + 0.0721750 B$.
   Apply black-level flare compensation:
   $$Y_s = \begin{cases} Y + (0.022 - Y)^{1.414} & \text{if } Y < 0.022 \\ Y & \text{otherwise} \end{cases}$$

2. **Lightness Contrast ($L_c$)**:
   - **Normal Polarity** (Dark text on light background, $Y_{\text{bg}} > Y_{\text{fg}}$):
     $$C = 1.14 \times \left( Y_{\text{bg}}^{0.56} - Y_{\text{fg}}^{0.57} \right)$$
     $$L_c = (|C| < 0.1) \ ? \ 0 : (C - 0.027) \times 100$$
   - **Reverse Polarity** (Light text on dark background, $Y_{\text{bg}} \le Y_{\text{fg}}$):
     $$C = 1.14 \times \left( Y_{\text{bg}}^{0.65} - Y_{\text{fg}}^{0.62} \right)$$
     $$L_c = (|C| < 0.1) \ ? \ 0 : (C + 0.027) \times 100$$

**APCA Thresholds for Terminal & Code Contexts**:
- $|L_c| \ge 75$: Ideal for main code/text body.
- $|L_c| \ge 60$: Minimum acceptable contrast for standard 12–14pt monospace code.
- $|L_c| \ge 45$: Acceptable for large text, bold keywords, or secondary elements (e.g., comments, line numbers).
- $|L_c| < 40$: Problematic / low readability.
- $|L_c| < 30$: Failing / invisible text.

### 2.4. The Oklab / Oklch Color Space (Perceptual Uniformity)
While CIELAB ($L^*a^*b^*$) has been the historic standard, it suffers from severe perceptual non-uniformities—most notoriously the **blue shift** (where increasing saturation shifts blue toward purple). Furthermore, calculating perceptual differences in CIELAB requires **CIEDE2000 ($\Delta E_{00}$)**, which involves complex piecewise trigonometric functions, rotation terms ($R_T$), and hue-angle corrections that are prone to implementation bugs.

**Oklab** (Björn Ottosson, 2020) solves this. It was fit directly against CAM16 numerical datasets so that:
1. Lightness ($L$) aligns with human perceived brightness.
2. Chroma ($C$) and Hue ($h$) are uniform.
3. **Perceptual color difference is simply Euclidean distance**:
   $$\Delta E_{\text{Ok}} = \sqrt{(L_1 - L_2)^2 + (a_1 - a_2)^2 + (b_1 - b_2)^2}$$

#### Transformation Pipeline: Linear sRGB $\to$ Oklab

**Step 1: Linear sRGB to Cone Space ($LMS$)**:
$$\begin{bmatrix} l \\ m \\ s \end{bmatrix} = \begin{bmatrix}
0.4122214708 & 0.5363325363 & 0.0514459929 \\
0.2119034982 & 0.6806995451 & 0.1073969566 \\
0.0883024619 & 0.2817188376 & 0.6299787005
\end{bmatrix} \begin{bmatrix} R_{\text{linear}} \\ G_{\text{linear}} \\ B_{\text{linear}} \end{bmatrix}$$

**Step 2: Non-linear Cube-Root Compression**:
$$L' = \sqrt[3]{l}, \quad M' = \sqrt[3]{m}, \quad S' = \sqrt[3]{s}$$

**Step 3: $LMS \to$ Oklab ($L, a, b$)**:
$$\begin{bmatrix} L_{\text{ok}} \\ a_{\text{ok}} \\ b_{\text{ok}} \end{bmatrix} = \begin{bmatrix}
0.2104542553 & 0.7936177850 & -0.0040720468 \\
1.9779984951 & -2.4285922050 & 0.4505937099 \\
0.0259040371 & 0.7827717662 & -0.8086757660
\end{bmatrix} \begin{bmatrix} L' \\ M' \\ S' \end{bmatrix}$$

**Step 4: Oklch Conversion**:
$$C_{\text{ok}} = \sqrt{a_{\text{ok}}^2 + b_{\text{ok}}^2}$$
$$h_{\text{ok}} = \left(\text{atan2}(b_{\text{ok}}, a_{\text{ok}}) \times \frac{180}{\pi}\right) \pmod{360}$$

#### Perceptual Distance ($\Delta E_{\text{Ok}}$) Interpretation:
- $\Delta E_{\text{Ok}} < 0.02$: Imperceptible difference (sub-JND).
- $0.02 \le \Delta E_{\text{Ok}} < 0.05$: Just Noticeable Difference (JND).
- $\Delta E_{\text{Ok}} < 0.07$: **Syntax Highlighting Collision**. Two distinct tokens will look virtually identical to human eyes in rapid reading.
- $\Delta E_{\text{Ok}} \ge 0.10$: Clearly distinct tokens.

### 2.5. Color Vision Deficiency (CVD) Simulation
To audit accessibility for colorblind developers, colors must be projected into simulated dichromacy spaces using linear sRGB transformation matrices (Viénot, Brettel, & Mollon 1999; Machado et al. 2009):

$$\mathbf{C}_{\text{sim}} = \mathbf{M}_{\text{CVD}} \cdot \mathbf{C}_{\text{linear}}$$

| Deficiency | Affected Cones | Prevalence (Males) | $3 \times 3$ Transformation Matrix $\mathbf{M}_{\text{CVD}}$ |
|---|---|---|---|
| **Protanopia** | L-cone (Red-blind) | ~1.3% | $\begin{bmatrix} 0.56667 & 0.43333 & 0.00000 \\ 0.55833 & 0.44167 & 0.00000 \\ 0.00000 & 0.24167 & 0.75833 \end{bmatrix}$ |
| **Deuteranopia** | M-cone (Green-blind) | ~1.2% (~5% anomaly) | $\begin{bmatrix} 0.62500 & 0.37500 & 0.00000 \\ 0.70000 & 0.30000 & 0.00000 \\ 0.00000 & 0.30000 & 0.70000 \end{bmatrix}$ |
| **Tritanopia** | S-cone (Blue-blind) | ~0.01% | $\begin{bmatrix} 0.95000 & 0.05000 & 0.00000 \\ 0.00000 & 0.43333 & 0.56667 \\ 0.00000 & 0.47500 & 0.52500 \end{bmatrix}$ |

## 3. The ANSI Colorscheme Audit Specification

An auditor should execute a deterministic suite of rules categorized into three severities:
- `FAIL`: Severe defect causing illegibility, broken terminal semantics, or accessibility violations.
- `WARN`: Sub-optimal contrast, inverted brightness, or collision risk.
- `INFO`: Style observations, gamut coverage, and chromatic balance.

### 3.1. Rule Suite Definition

#### Rule A: Background Contrast (Legibility)
- **Check**: Every text color (ANSI 1–7, 9–15, and foreground) against `background`.
- **Criteria**:
  - `FAIL` if WCAG $< 3.0:1$ or APCA $|L_c| < 45$.
  - `WARN` if WCAG $< 4.5:1$ or APCA $|L_c| < 60$.
  - `PASS` if WCAG $\ge 4.5:1$ and APCA $|L_c| \ge 60$.

#### Rule B: Comment & Muted Contrast (ANSI 8 / Bright Black)
ANSI 8 is the most abused color in terminal theming:
- **Criteria**:
  - `FAIL` if ANSI 8 against `bg` has APCA $|L_c| < 35$ (unreadable comments).
  - `WARN` if ANSI 8 has APCA $|L_c| < 45$.
  - `WARN` if $L_{\text{ok}}(\text{ANSI 8}) \ge L_{\text{ok}}(\text{ANSI 7})$ (comments should be visually subordinate to normal text).

#### Rule C: Monotonicity & Bright-Pair Hierarchy
In dark themes, "bright" variants should be perceived as brighter or equal in lightness to their normal counterparts:
- **Criteria**:
  - For each hue pair $i \in \{1 \dots 6\}$:
    - Normal color: ANSI $i$
    - Bright color: ANSI $i + 8$
    - Check: $L_{\text{ok}}(\text{ANSI } i+8) \ge L_{\text{ok}}(\text{ANSI } i) - 0.01$
    - `WARN` if $L_{\text{ok}}(\text{ANSI } i+8) < L_{\text{ok}}(\text{ANSI } i)$ (Inverted brightness: bold text appears darker than normal text).
  - For monochrome scale:
    - Dark theme: $L_{\text{ok}}(\text{bg}) \le L_{\text{ok}}(\text{ANSI 0}) < L_{\text{ok}}(\text{ANSI 8}) < L_{\text{ok}}(\text{ANSI 7}) \le L_{\text{ok}}(\text{ANSI 15})$

#### Rule D: Syntax Token Collision ($\Delta E_{\text{Ok}}$ Separation)
Syntax highlighters rely on differentiating tokens (Red, Green, Yellow, Blue, Magenta, Cyan).
- **Check**: Compute pairwise $\Delta E_{\text{Ok}}$ between all normal colors $\{1, 2, 3, 4, 5, 6\}$.
- **Criteria**:
  - `FAIL` if any pair has $\Delta E_{\text{Ok}} < 0.04$ (severe indistinguishability).
  - `WARN` if any pair has $\Delta E_{\text{Ok}} < 0.07$ (token collision in code).

#### Rule E: Git Diff & Semantic CVD Discriminability
In diffs, ANSI 1 (Red/deletion) and ANSI 2 (Green/addition) are juxtaposed:
- **Check**: Under Protanopia and Deuteranopia simulation:
  1. Compute $\Delta E_{\text{Ok}}(\text{sim}(\text{Red}), \text{sim}(\text{Green}))$.
  2. Compute $|\Delta L_{\text{ok}}| = |L_{\text{ok}}(\text{sim}(\text{Red})) - L_{\text{ok}}(\text{sim}(\text{Green}))|$.
- **Criteria**:
  - `FAIL` if $\Delta E_{\text{Ok}} < 0.05$ AND $|\Delta L_{\text{ok}}| < 0.06$. (Red and Green are identical for colorblind users).
  - *Mitigation*: Themes must either give Red and Green distinct lightness ($L$) or distinct yellow-blue chromaticity ($b^*$) so they remain differentiable.

#### Rule F: Hue Sector Fidelity (Identity Verification)
Validates that ANSI slots actually reflect their standard color identities using Oklch hue angle ($h_{\text{ok}} \in [0^\circ, 360^\circ)$):

| ANSI Slot | Name | Expected Hue Range ($h_{\text{ok}}$) |
|---|---|---|
| **ANSI 1 / 9** | Red / Bright Red | $15^\circ - 50^\circ$ (or $350^\circ - 360^\circ$) |
| **ANSI 2 / 10** | Green / Bright Green | $115^\circ - 165^\circ$ |
| **ANSI 3 / 11** | Yellow / Bright Yellow | $75^\circ - 110^\circ$ |
| **ANSI 4 / 12** | Blue / Bright Blue | $230^\circ - 280^\circ$ |
| **ANSI 5 / 13** | Magenta / Bright Magenta | $305^\circ - 350^\circ$ |
| **ANSI 6 / 14** | Cyan / Bright Cyan | $175^\circ - 225^\circ$ |

- **Criteria**:
  - `WARN` if a color's hue falls entirely outside its expected perceptual sector (e.g., ANSI 4 Blue assigned to a teal or violet hue).

#### Rule G: Selection & Cursor Inversion
- **Criteria**:
  - Cursor must have APCA $|L_c| \ge 45$ against `background`.
  - Selection background must provide APCA $|L_c| \ge 30$ against `foreground` (or selection text must be legible).

## 4. Architecture: Extreme Correctness Yet Simple

To ensure the auditor is both easy to maintain and runs anywhere (Neovim, command line, CI pipelines), the design adheres to the following principles:

```
[ Palette Input ]  -->  Hex, TOML, Kitty, Xresources, or OSC 4/11 query
        |
        v
[ color_math.lua ] -->  Linear sRGB, Oklab/Oklch, APCA, WCAG 2.1, CVD Projections
        |
        v
[ auditor.lua ]    -->  Pure rule engine (runs Rules A–G, emits diagnostics table)
        |
        v
[ reporter.lua ]   -->  Outputs human CLI report (colored ANSI) or machine JSON
```

### 4.1. Core Module: `color_math.lua`
Contains the pure mathematical foundations with zero dependencies:
- Exact IEEE 754 float operations.
- Direct matrix multiplications (unrolled for performance).
- Deterministic conversions without floating-point drift.

```lua
-- color_math.lua snippet
local M = {}

function M.hex_to_rgb(hex)
  hex = hex:gsub("#", "")
  if #hex == 3 then
    hex = hex:sub(1,1):rep(2) .. hex:sub(2,2):rep(2) .. hex:sub(3,3):rep(2)
  end
  local num = tonumber(hex, 16)
  if not num then return nil end
  return {
    r = bit32 and bit32.rshift(num, 16) / 255 or math.floor(num / 65536) / 255,
    g = bit32 and bit32.band(bit32.rshift(num, 8), 0xff) / 255 or math.floor((num % 65536) / 256) / 255,
    b = bit32 and bit32.band(num, 0xff) / 255 or (num % 256) / 255,
  }
end

function M.srgb_to_linear(c)
  return c <= 0.04045 and (c / 12.92) or (((c + 0.055) / 1.055) ^ 2.4)
end

function M.rgb_to_oklab(rgb)
  local r = M.srgb_to_linear(rgb.r)
  local g = M.srgb_to_linear(rgb.g)
  local b = M.srgb_to_linear(rgb.b)

  local l = 0.4122214708 * r + 0.5363325363 * g + 0.0514459929 * b
  local m = 0.2119034982 * r + 0.6806995451 * g + 0.1073969566 * b
  local s = 0.0883024619 * r + 0.2817188376 * g + 0.6299787005 * b

  local l_ = l ^ (1 / 3)
  local m_ = m ^ (1 / 3)
  local s_ = s ^ (1 / 3)

  local L = 0.2104542553 * l_ + 0.7936177850 * m_ - 0.0040720468 * s_
  local a = 1.9779984951 * l_ - 2.4285922050 * m_ + 0.4505937099 * s_
  local b_val = 0.0259040371 * l_ + 0.7827717662 * m_ - 0.8086757660 * s_

  return { L = L, a = a, b = b_val }
end

function M.oklab_to_oklch(oklab)
  local c = math.sqrt(oklab.a * oklab.a + oklab.b * oklab.b)
  local h = math.atan2(oklab.b, oklab.a) * (180 / math.pi)
  if h < 0 then h = h + 360 end
  return { L = oklab.L, C = c, h = h }
end

function M.delta_e_ok(lab1, lab2)
  local dL = lab1.L - lab2.L
  local da = lab1.a - lab2.a
  local db = lab1.b - lab2.b
  return math.sqrt(dL * dL + da * da + db * db)
end

function M.apca(rgb_fg, rgb_bg)
  local function to_y(rgb)
    local r = rgb.r ^ 2.4
    local g = rgb.g ^ 2.4
    local b = rgb.b ^ 2.4
    local y = 0.2126729 * r + 0.7151522 * g + 0.0721750 * b
    if y < 0.022 then
      y = y + (0.022 - y) ^ 1.414
    end
    return y
  end

  local y_fg = to_y(rgb_fg)
  local y_bg = to_y(rgb_bg)

  local c
  if y_bg > y_fg then
    c = 1.14 * (y_bg ^ 0.56 - y_fg ^ 0.57)
    if math.abs(c) < 0.1 then return 0.0 end
    c = c - 0.027
  else
    c = 1.14 * (y_bg ^ 0.65 - y_fg ^ 0.62)
    if math.abs(c) < 0.1 then return 0.0 end
    c = c + 0.027
  end
  return c * 100.0
end
```

### 4.2. Palette Input Adaptability
The auditor accepts a standard Lua table:
```lua
local palette = {
  bg = "#1e1e2e",
  fg = "#cdd6f4",
  cursor = "#f5e0dc",
  selection = "#45475a",
  [0]  = "#45475a", -- Black
  [1]  = "#f38ba8", -- Red
  [2]  = "#a6e3a1", -- Green
  [3]  = "#f9e2af", -- Yellow
  [4]  = "#89b4fa", -- Blue
  [5]  = "#f5c2e7", -- Magenta
  [6]  = "#94e2d5", -- Cyan
  [7]  = "#bac2de", -- White
  [8]  = "#585b70", -- Bright Black
  [9]  = "#f38ba8", -- Bright Red
  [10] = "#a6e3a1", -- Bright Green
  [11] = "#f9e2af", -- Bright Yellow
  [12] = "#89b4fa", -- Bright Blue

  [14] = "#94e2d5", -- Bright Cyan

```

It can also query the active terminal directly via ANSI **OSC 4 / 10 / 11** sequences:
- `\x1b]10;?\x1b\\` (Foreground query)
- `\x1b]11;?\x1b\\` (Background query)
- `\x1b]4;i;?\x1b\\` (Palette index $i$ query)

Terminal replies return in standard `rgb:rrrr/gggg/bbbb` 16-bit format, which the schema parser normalizes.

## 5. Summary of Recommended Checks & Thresholds

| Check | Primary Metric | Fail Threshold | Warn Threshold | Pass Ideal |
|---|---|---|---|---|
| **Text Contrast** | APCA $L_c$ & WCAG 2.1 | $\|L_c\| < 45$ or WCAG $< 3.0$ | $\|L_c\| < 60$ or WCAG $< 4.5$ | $\|L_c\| \ge 60$, WCAG $\ge 4.5$ |
| **Comments (ANSI 8)** | APCA $L_c$ | $\|L_c\| < 35$ or $> L(\text{fg})$ | $\|L_c\| < 45$ | $45 \le \|L_c\| \le 55$ |
| **Pair Distinction** | Oklab $\Delta E_{\text{Ok}}$ | $\Delta E_{\text{Ok}} < 0.04$ | $\Delta E_{\text{Ok}} < 0.07$ | $\Delta E_{\text{Ok}} \ge 0.10$ |
| **CVD Diff Readability** | Protan/Deutan $\Delta E_{\text{Ok}}$ | $\Delta E_{\text{Ok}} < 0.05$ & $\|\Delta L\| < 0.06$ | $\Delta E_{\text{Ok}} < 0.08$ & $\|\Delta L\| < 0.08$ | $\Delta E_{\text{Ok}} \ge 0.10$ or $\|\Delta L\| \ge 0.12$ |
| **Bright Hierarchy** | Oklab $L_{\text{ok}}$ | $L_{\text{bright}} < L_{\text{norm}} - 0.03$ | $L_{\text{bright}} < L_{\text{norm}}$ | $L_{\text{bright}} \ge L_{\text{norm}} + 0.03$ |
| **Hue Fidelity** | Oklch $h_{\text{ok}}$ | (None) | Hue outside canonical band | Hue centered in perceptual band |
